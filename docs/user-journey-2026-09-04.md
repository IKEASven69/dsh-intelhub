# 用户使用场景与交互流程 · 完整文档

> 2026-09-04 ｜ 基于 0.5.0 全部已交付功能 ｜ 已审阅并标注 3 处不合理/缺口
> 定位：**hippo = 个人工作上下文的所有权层。agent 是租客：来了取、干活时还、走了不带走。**

---

## 一、用户画像

| | 说明 |
|---|---|
| **主用户** | 单机、多 agent 并行（WorkBuddy / zcode / Claude Code / Codex），每天在 2~4 个 agent 之间切换 |
| **核心痛点** | 切 agent 时要口述上下文；踩过的坑下次还踩；"昨天做到哪了"答不上来 |
| **拒绝的** | 手动写交接文档；每次切 agent 要口述背景；记忆库变成垃圾场 |

## 二、一次完整的周使用周期

### 场景 1：周一开工

**用户动作：** 打开 dsh → 新会话 → 说"继续上次的 auth 重构"

**系统（自动）：**
```
agent 开局收到薄索引（≤100 token）：
  活跃任务 3 条 · 项目 dsh-plugin · 分支 main
  1. auth 重构 in_progress ← 周五在做的
  2. minimax Token Plan 接入 completed
  3. WorkBuddy 适配器 pending

  高置信记忆：
  · [决策] 认证统一走 auth 模块
  · [教训] 构建必须先过 tsc
```

**成本：约 85 token。不需要说"接手"，agent 天然知道该干什么。**

---

### 场景 2：日常干活（周二~周四）

**用户动作：** 在 zcode 改代码，同时在 WorkBuddy 调研方案，在 Claude Code 写文档。三个 agent 随便切。

**系统（后台每 15 分钟自动执行）：**
```
transcript → 噪音闸门（拦过程自语/标题/样板文）
           → LLM 精炼（minimax，改写为自包含陈述）
           → 去重分档（≥0.93 强化 / 0.8~0.93 待审 / <0.8 新建）
           → supersede 检测（翻转词 + 高相似 → 旧版沉底）
           → 入库
```

**跨 agent 效果：** 你在 zcode 里说"不用 Redux 太重了，改 Zustand"——切到 WorkBuddy 问"状态管理用什么？"——agent 调 memory_recall → 命中 → 直接回答。**不需要你重复。**

---

### 场景 3：踩了个坑

**用户动作：** 在 zcode 里发现 `grep -c` 会把子串也算进去——继续干活，不做任何额外操作。

**系统（后台自动）：**
- 自动蒸馏提取教训："grep -c 会把子串也算进去（15173 包含 5173），用 grep -w 精确匹配"
- 入库。下次任何 agent 在同类场景用 grep -c 时，recall 命中 → 提醒

---

### 场景 4：任务做完

**用户动作：** 在 agent 里正常标记任务完成。

**系统（零动作）：**
```
任务完成 → 卡点 + 解法 + 当时 branch/changed → minimax 压缩摘要 → 入库
```

三个月后遇到类似问题，任何 agent 调 recall 直接命中这条教训——带完整上下文（当时改了什么文件、为什么这么选）。

---

### 场景 5：跨 agent 交接

**用户动作：** 在 zcode 里干到一半，要在 WorkBuddy 里继续。

**操作路径 A（一行命令/按钮）：**
1. 工作台会话页 → 找到当前会话 → 点 **⇪**
2. 选目标 agent → 点推送
3. 打开 WorkBuddy → 开局自动收到完整上下文

**操作路径 B（自然对话）：**
1. 在 WorkBuddy 里说"继续 auth 重构"
2. agent 自主调 memory_recall → 命中相关记忆 → 接上进度

**两条路径都是零口述。**

---

### 场景 6：周五收工

**用户动作：** 关电脑去玩。

**系统（后台自动）：**
- sleep 整合（近重复合并，supersede 可逆，原文可溯）
- tier 老化归档（90 天前旧记忆按项目+月卷成摘要，LLM 压缩）
- 零召回检测（从未被召回的记忆标记）
- AGENTS.md 自动重编译
- memory_feedback 日志持续积累（供判决挖掘）

**你周一回来，一切就绪。**

## 三、⚠ 审阅发现的漏洞与不合理之处

### 🔴 缺口 1：冷启动——第一次装完是空的

**场景**：新用户装完插件，打开工作台——0 条记忆，什么都没有。

**问题**：一键迁移按钮在那儿，但用户不知道要点它。而且 343 个会话全量蒸馏需要时间（几分钟到十几分钟），用户可能等不了。

**当前缓解**：doctor 自检 + 会话发现面板 + 迁移进度条。但**首次体验仍然是"装完→空的→ 要等"**。

**需补**：
- 首次安装后自动弹出引导（"检测到 341 个会话，点开始迁移"）
- 迁移过程中显示渐进结果（"已从 Claude Code 提取 45 条…"），让用户有信心等
- 迁移完成后自动触发一次 recall 演示（"看，这就是你的记忆"）

### 🟡 缺口 2：Agent 不调 recall 怎么办

**场景**：agent 在干活，但你提了一个有相关记忆的问题——agent **没有主动调 memory_recall**，直接凭模型知识回答了。

**问题**：工具描述写了"回答之前怎么定的/踩过什么坑类问题先查它"，但 agent 的自主判断不稳定。有时候会调，有时候不会。

**当前缓解**：薄索引注入让 agent 开局就知道高置信记忆（不需要调工具）。

**需补**：
- 提示注入中加强引导："当用户问'怎么做/为什么/之前是否'类问题时，先调 memory_recall"
- 或：在 handoff_load / context_fold 的回执中显式写"本项目的记忆可通过 memory_recall 检索"

### 🟡 缺口 3：多 agent 同时写同一项目

**场景**：你在 zcode 和 WorkBuddy 里同时打开同一项目。两个 agent 的 auto-distill 同时跑。

**问题**：zvec 单写锁——两个进程不能同时写。后到的会等锁或失败。

**当前缓解**：engine-holder 引用计数 + 短持锁，实测双入口共存正常。但这是**读多写少**场景下的表现。如果两个 agent 的 auto-distill 定时器恰好同时触发，可能出现锁等待。

**需补**：
- auto-distill 加分布式锁/队列（或至少加随机延迟错开）
- 监控日志中 "锁等待" 出现频率

### 🟢 做对了的（不需要改）

| 设计 | 为什么对 |
|---|---|
| 会话是一等公民 | transcript 永不丢 → 记忆丢了可以重新蒸馏（本人在测试中亲身验证了这一点） |
| supersede 可逆链 | 改错了、归档错了、合并错了——都能恢复 |
| 消费即弃 | 上下文不残留，不膨胀 |
| 噪音闸门 + LLM 精炼 | 267 条零召回垃圾被拦在库外 |
| Memoryfields 透明格式 | 用户随时可以 grep/cat 自己的记忆，数据自主权 |
| 双入口共存 | dsh 插件 + 独立 GUI 共享数据，不互锁 |

## 四、使用效果量化（实际数据）

| 指标 | 无 hippo | 有 hippo |
|---|---|---|
| 跨 agent 交接 | 口述 5~10 分钟 | **零操作**（开局自动注入） |
| 切 agent 后"昨天做到哪" | 答不上来 | **薄索引 85 token 自动回答** |
| 踩坑教训 | 随会话蒸发 | **自动入库，3 个月可召回** |
| 记忆噪声率 | — | **~4%**（598 条中仅 4% 不值得留，LLM 精炼后） |
| 上下文成本 | 全文文档 1500+ token | **薄索引 85 token** |
| 检索延迟 | — | 语义混合 **<1 秒**（缓存后） |

## 五、不同角色的入口

| 入口 | 用户 | 怎么进 |
|---|---|---|
| **dsh 插件** | dsh 用户 | 设置 → 记忆桥 → 🦛 打开完整工作台 |
