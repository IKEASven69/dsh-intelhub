## 1. 智能上下文注入（当前最大体验差距）

### 1.1 现状（实测代码审计）

当前注入逻辑（`tools.ts:130-155`）：
```
scan 全库 → filter(project == current && strength >= 2) → sort(strength DESC) → top 3
```

**问题**：这是静态的——不管你在改 auth 模块还是部署脚本，注入的都是同样的"strength 最高"三条。改 auth 时看到的是"暗号是紫色河马"，完全无关。

### 1.2 差距分析

| 维度 | 现状 | 应该 |
|---|---|---|
| 上下文信号 | 零（只有 project 名） | 当前编辑文件路径 + 最近对话话题 + git branch |
| 选择策略 | strength 降序 top 3 | 语义相关性排序（recall 而非 scan） |
| 类型多样性 | 无（可能 3 条全是 preference） | 决策/教训/偏好混合 |
| 注入成本 | scan 全量（同步，快） | recall（嵌入计算，首次慢后缓存） |

### 1.3 方案

**两阶段注入**（保持零延迟+加语义）：
1. **同步层**（不变）：strength top 3，<100 token，保证零延迟
2. **异步增强**（新增）：在 agent 开始工作后，后台跑一次 `memory_recall(当前文件路径关键词)`，结果追加到上下文（不阻塞）

改动量：`tools.ts` 的 `text()` 函数加一个 `filePath` 信号 → `recall(filePath 关键词, limit 2)` 追加。改动约 30 行。

### 1.4 竞品对比

| 竞品 | 注入方式 | 我们差什么 |
|---|---|---|
| mem0 | 每轮对话后 LLM 提取事实→自动 ADD/UPDATE/DELETE | 它有实时记忆更新，我们靠事后蒸馏 |
| Cursor Rules | 静态 .cursorrules 文件 | 我们已有（AGENTS.md 编译）✅ |

| unblocked | 跨源 join（Slack/Jira/GitHub） | 我们只有 agent 会话，没接 IDE 上下文 |

## 2. 冲突检测与解决

### 2.1 现状（三层，已有两层）

| 层 | 机制 | 覆盖场景 |
|---|---|---|
| **写入时** | FLIP_PATTERN 显式翻转词 + SUPERSEDE_FLOOR 0.85 | "改用 X" 类显式改主意 |
| **查询时** | supersededPenalty 0.4（被取代的降权） | 推翻链自动降权 |
| **事后发现** | ❌ 无——矛盾的两条各自独立存在，没人发现它们矛盾 | **这是缺口** |

### 2.2 mem0 对比

mem0 的冲突处理：新记忆入库时，LLM 决策 `ADD`（新信息）/ `UPDATE`（更新旧条）/ `DELETE`（矛盾删除）/ `NOOP`（无冲突）。

**我们的优势**：supersede 链保留了旧版（可审计、可恢复），mem0 的 DELETE 是真删。
**我们的劣势**：没有 LLM 自动发现隐式矛盾——依赖显式翻转词。

### 2.3 补全方案

**自动冲突扫描**（不需要 LLM）：
- 扫描同项目 sim ≥ 0.75 且未 supersede 的记忆对
- 检测否定词不对称（一条含"不用/放弃"，另一条不含）
- 结果进 conflicts 队列 → 人工裁决

**GUI 冲突解决界面**：
- 会话页顶部提示条："发现 N 条矛盾记忆"
- 点开逐条对比（A vs B 并排展示）
- 操作：保留 A / 保留 B / 合并 / 都删
- 操作走 markSuperseded（可逆）
