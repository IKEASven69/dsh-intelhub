# dsh-deck 定位与差异化 · 校准笔记

> 触发：2026-08 体验「豆包工作」（豆包 + 飞书融合的办公 Agent 工作台）后的定位反思。
> 结论：豆包工作验证了「Agent 入口 + 上下文护城河」方向，但走的是云 + 飞书组织路线；dsh-deck 走本地优先 + 平台无关的个人路线，二者不冲突。dsh 的护城河需从「功能罗列」升级为「个人本地上下文主权」。

## 一、行业信号（来自豆包工作体验）

1. **入口迁移**：人先开 Agent，再让 Agent 操作应用，应用退为后台工具。习惯一旦形成难逆转——入口在哪，注意力就在哪，生态就在哪。
2. **红海与护城河**：Harness（写文档/表/PPT/浏览器）差距迅速抹平；真正差距在 Agent 能访问的**组织上下文**——会议、文档、群聊、项目脉络。谁有最完整上下文，谁的服务最准。
3. **权限是分水岭**：个人可随意，企业必须继承既有权限体系（看不到 = Agent 看不到，未授权 = 不能做）。内建权限/身份的平台有先天优势。
4. **个人提效 ≠ 组织提效**：流程围绕人搭建，Agent 只在局部提效。解法是围绕 Agent 重构流程，确认环节交 Agent 自验证，人只在关键路径拍板。
5. **Agent 接管执行，人向上走**：更多精力花在判断、取舍、创新。

## 二、对 dsh-deck 的映射（已落在设计里）

- 入口迁移 → **总台**（对话↔工作台桥）+ **消息台**（通讯收进 Agent，opencli 写回）
- 上下文护城河 → **知识库**（5486 篇）+ 灵感库 + 复盘 + 关注人
- 权限 → dsh 对应「**数据主权**」：opencli 驱动用户自己的已登录浏览器，发文/抓数据以「你」的身份发生，数据不出本机、不上传第三方 AI 账号
- 个人 ≠ 组织提效 → **总台待办**带状态，AI 起草、人点发
- 人向上走 → 内容台自动发布、消息台写回

## 三、定位重述（关键修正）

旧表述（偏弱，像功能罗列）：开放 + agentic + 本地优先 + 平台无关。

新表述（护城河锚点）：

> **dsh-deck 的护城河 = 个人本地上下文主权。**
> 你多年沉淀的知识库、关注人、项目脉络、复盘结论、灵感流，存在你自己的机器上，不被任何云收割，也不因换模型/换平台而丢失。
> 飞书离「组织上下文护城河」近，是因为它是组织信息汇聚地；dsh 离「个人上下文护城河」近，是因为它本地优先 + 平台无关——这是豆包工作结构上给不了的东西（锁在飞书云、模型锁豆包）。

**opencli = 逃生舱**：浏览器驱动任意平台，无需官方 API、不把数据交给 Big-Tech AI。

## 四、对架构的三条设计含义

1. **知识库从「平级台」升级为「上下文脊柱」**：灵感库 / 调研台 / 消息台 / 内容台都从它读、往它写。对外叙事变成「你的个人上下文归你所有」。
2. **定位文档重写**：从「开放 + 平台无关」升级为「个人本地上下文主权 + 平台无关逃生舱」。
3. **不必为对标砍 breadth**：豆包工作是办公 / 企业场景；dsh 是 solo 创作者（多仓库 + 社媒 + 知识库），场景不同，5 台结构保留。

## 五、不对标的部分

- 不做企业权限继承（无飞书 / 组织体系可接）
- 不锁模型（本地优先 → 可换本地 / 任意 API，豆包锁豆包）
- 不锁平台（opencli 跨平台，飞书锁飞书）
